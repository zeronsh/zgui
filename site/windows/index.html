zgx performance · Windows · 2026-10-27

zgx uses the least CPU in 10 of 10 tests and the least app GPU time in 8, against GPUI Fast, MyGo and Rune.

zgx against GPUI Fast (Zed's GPUI with its fast-path optimizations, as apps ship it) MyGo (a Go desktop framework, through its GPU-drawn native UI) and Rune (Rust, wgpu, Taffy and Parley): the same four scenes, built from the same workload code, measured on one Windows PC in one session. Startup

From launch to the window’s first content, 10 launches of each in rotating order: the probe starts the app (the lab scene, idle, in the suite’s font), waits for its window, then reads the top of its content as the window drew it until the first text has drawn, and reads the process’s CPU time and cycles at that moment. zgx shows its window with its first frame; MyGo and Rune show theirs before they draw. Measured after the suite, on the same PC, at ffbae9d.

How this was measured

  • Machine: 12th Gen Intel(R) Core(TM) i7-12700KF (20 logical processors, 31 GB), NVIDIA GeForce RTX 4090 (driver 617.42), Windows 11 (10.0.26200), AC Power, the High performance power plan held for the run.
  • Displays: 1 × SudoMaker Virtual Display Adapter (1920 x 1080 @ 60Hz); the window on the main display, brought to the front, nothing covering it.
  • Builds: zgx and GPUI Fast with their dist profile (release, fat LTO, one codegen unit), rustc 1.99.1 (58cf8f9c3 2026-10-13); MyGo v0.6.3 (1524290, MIT) built with go1.27.1 windows/amd64, go build -trimpath -ldflags=-s -w, cgo off; Rune at (dev, MIT), profile dist (Rune's perf with fat LTO and codegen-units 1) (Rune's own bench scripts use perf), and a 14-line patch exposing its wheel path (see below). Every framework uses the system allocator. zgx at ffbae9d.
  • Trials: each a fresh launch, the first 5 s after its window was ready (frontmost and uncovered) discarded and the next 10 s sampled; 3 trials of each mode, in alternating order, and 1 more of any whose CPU cycles or app GPU time spread past 10% of its median; idle 2 times in the dashboard, 20–30 s after its window was ready. Every trial had to run as long as asked, at 60 updates a second, its window uncovered as its sample began and ended. Medians are shown, the trials' range beside them. Frame timing is 3 separate 8 s captures of each mode.
  • CPU: the app process’s CPU cycles over the sample (QueryProcessCycleTime), in millions a second. Windows counts CPU time in scheduler ticks of 15.6 ms, too coarse for these loads (one app’s same animation read 0.9% and 0.3% of a core in two trials of equal cycles), so cycles are the figure; CPU time stays in the raw data.
  • CPU cycles per frame: the same cycles per update, or in the animation per frame drawn: what each frame costs, whatever the frame rate.
  • DWM CPU: the CPU cycles of the Desktop Window Manager (dwm.exe), Windows’ compositor, over the same sample, in millions a second: what showing the app costs the system beside the app’s own CPU. Read from the system’s process list (SystemProcessInformation’s cycle time), which needs no administrator rights where QueryProcessCycleTime needs a handle DWM gives no other user. It includes what DWM does anyway (the desktop alone, measured each repeat, is beside each chart’s title).
  • App GPU time: the time the GPU’s 3D engines ran the app’s work, from Windows’ GPU engine counters, in milliseconds a second. Windows reads no system GPU power, so this is the GPU figure here: how long the GPU was held, not what it spent.
  • DWM GPU time: the compositor’s time on the GPU’s 3D engines over the same sample: the GPU cost of putting the app’s frames on screen, plus what DWM does anyway (the desktop alone is beside each chart’s title).
  • Frame time: the 99th percentile of the intervals between frames shown on screen, read through Desktop Duplication (each frame the compositor put on screen in which the window’s pixels changed); at 60 updates a second, 16.7 ms is on time. Long frames are intervals over 25 ms.
  • Memory: the process’s private bytes (the memory it committed: Task Manager’s commit size), averaged over the sample.
  • The list widgets: zgx's measured virtual list, the same list from a Luau script (ui.list { measured = true }), and GPUI Fast's list measure each row as they lay it out; MyGo's ui.List keeps its place by an anchor row and estimates unmeasured rows at the average height; Rune's virtual rows estimate unmeasured rows (28 pt fixed, a three-line row variable) and measure as they mount.

How Rune is driven

  • Ticks through AppHandle::update_if. Rune's per-frame poll, woken by wake_after, ran on frame boundaries up to 16 ms late and dropped about 5% of ticks. A timer thread now hands each tick to the UI thread through update_if, Rune's API for a timer or feed, and waits for it to run, as the other adapters' loops do. This changes the measurement: Rune now does the same 60 ticks a second of work as the others.
  • Updates apply at once (Tx::instant). Rune animates every layout and colour change on a 0.3 s spring by default. Each tick is applied instantly, as the other frameworks apply live data. Leaving the springs on would add animation frames the other frameworks don't draw.
  • sRGB blending (App::srgb_blend(true)). Rune blends translucency in linear light by default, so 10% opacity looked brighter than in the others. Its documented sRGB mode matches CSS and the other three. It is a surface format and a shader flag, with no extra pass, so it changes pixels, not cost.
  • Heavy's panel contents sit 1 pt in. A Rune border takes no layout space, while CSS, which the scene's geometry follows, places absolute children inside the border. The children are offset by the border's width so that everything lands on the same pixels. Geometry only; the cost doesn't change.
  • vlist scrolls through a small patch exposing Rune's own wheel path (rune-wheel.patch, 14 lines). Rune's public API can't set a vertical scroll offset, and only user wheel input moves a list. The patch adds Tx::wheel, which feeds the same Runtime::wheel_xy a real wheel event goes through, at once, between frames. Nothing else in Rune changes. This is what makes Rune's scroll and fling measurable; it adds no work of its own.
  • Jump reveals the row (nearest), not at the top. Rune's scroll_into_view scrolls just far enough to show a row, where the other adapters put the jumped-to row at the top. A jump still mounts and lays out the far rows, but the row lands at a different place in the viewport.
  • The vlist probe runs headless. Row heights are read from Rune's headless runtime, with the same font and 720 pt width, after revealing each row. A row's height doesn't depend on where it sits. Only the layout check uses this; it doesn't feed any measured figure.

Caveats

  • Since 2026-10-26 a trial’s sample starts from its window being ready (frontmost and uncovered, polled up to 2.5 s), not from its launch, and each app runs 3 s longer; this run is therefore not ranked against earlier ones, which measured from launch.
  • Compare within this run only: the same binaries measured hours apart read differently (the machine's state changes), so a cell is not comparable across runs, while the frameworks in one run share its session.
  • The display refreshes at 60Hz: the animation is drawn at that rate here, so its figures are not comparable with a page measured at another.
  • Where zgx is furthest behind the best rival in each metric (zgx’s median over the lowest rival’s, in its worst test; under 1 is less than every rival there):
    • CPU: 1.07× (heavy dashboard, idle: 1.6 M cycles/s against MyGo’s 1.5 M cycles/s)
    • CPU cycles per frame: 0.99× (animation, animating: 1.60 M cycles against GPUI Fast’s 1.61 M cycles)
    • DWM CPU: 1.03× (variable-height list, jumping: 143.7 M cycles/s against MyGo’s 140.0 M cycles/s)
    • App GPU time: 1.30× (heavy dashboard, both: 13.19 ms/s against Rune’s 10.15 ms/s)
    • DWM GPU time: 1.06× (variable-height list, jumping: 2.32 ms/s against MyGo’s 2.20 ms/s)
    • Frame time, 99th percentile: 1.90× (variable-height list, flinging: 33.3 ms against Rune’s 17.5 ms)
    • Long frames: 5.03× (variable-height list, flinging: 2.1% against Rune’s 0.4%)
    • Memory: 1.47× (text and a 100,000-row list, scrolling: 133 MB against GPUI Fast’s 91 MB)
  • MyGo is immediate mode: each frame it draws builds and draws its whole window, which is how MyGo apps work.
  • DWM spends more CPU on zgx’s window than on the cheapest rival’s in 2 of 10 tests, by at most 3.7 M cycles a second (its chart follows CPU in each scene).
  • Memory includes the graphics driver’s own floor, which differs by API. The processes had these loaded: zgx Direct3D 12; GPUI Fast Direct3D 11; MyGo Direct3D 11; Rune Direct3D 12 and OpenGL and Vulkan; zgx (Luau) Direct3D 12.
  • Until 2026-10-27 this page’s DWM CPU was DWM’s CPU time from performance counters, in % of a core. Windows counts that time in 15.6 ms scheduler ticks, so its trials spread widely and its ratios moved with the rivals’ noise. It is now DWM’s CPU cycles, in millions a second (see How this was measured); the tick-counted figure stays in the raw data.
  • A remote display host (sunshine) streamed the desktop throughout, capturing and encoding the screen: work beside every framework’s, in the desktop baseline too, which is why the run accepted up to 200% of a core of other use.
  • The list’s fling ends slowly, under a pixel a refresh for its last ticks (160 px a tick decaying to 0.6). zgx scrolls in whole device pixels, as Chrome and Windows’ own lists do, to keep text crisp, so in that tail some refreshes move nothing on screen and the capture counts them as long frames: zgx presented on every refresh, its GPU work done within 0.2 ms of each present. Scrolled at a steady 12 or 3 px a tick it shows none; at 0.6 px a tick, 36 frames a second of whole-pixel steps. Rune draws at fractional positions, which change its pixels on every tick.
  • The list scene’s unfilled-row captures are macOS’s only.
  • No app exited abnormally during the run.
  • Binary size is not compared.
  • One machine, one session; a personal PC in use, other applications kept running (the run waited until the machine was quiet, Zeron’s windows minimized). macOS is compared on its own page; Linux is not compared here.
