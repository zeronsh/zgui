<Method />

### What each figure is

- **CPU:** the app process's CPU time over the sample, as a percentage of one core (it can exceed 100).
- **WindowServer CPU:** the CPU of macOS's compositor, which puts every app's frames on screen, over the same sample: what showing the app costs the system beside the app's own CPU. It includes what WindowServer does anyway.
- **GPU power:** the whole GPU's energy over the sample, from the system's energy model (IOReport), in milliwatts, less the desktop alone (measured each repeat). It counts everything the GPU does for the app, the window server's compositing of its window included, so a framework is charged for how it presents its frames as well as for drawing them.
- **App GPU time** (secondary): the GPU time macOS accounts to the app's process, as cycles at the GPU's mean clock. It includes the time from each submission to the GPU starting it, so an app that draws small frames often reads high. Kept for comparison with earlier runs.
- **Frame time:** the 99th percentile of the intervals between frames shown on screen; at 60 updates a second, 16.7 ms is on time (8.3 ms for the animation, drawn at 120 Hz). **Long frames** are intervals over 25 ms.
- **Unfilled rows** (the list): the window captured 10 times a second while scrolling and jumping; a capture counts when a stretch of the rows' padding over 24 points shows the window's background, where no row was drawn.
- **Memory:** the process's physical footprint (what Activity Monitor shows: resident memory plus GPU memory it owns), averaged over the sample.

### Caveats

- Frame time and long frames are measured while the window is captured (ScreenCaptureKit), and capturing a window changes its pacing: macOS skips frames it would otherwise show, more for some ways of presenting than others. They show pacing under a capture (screen sharing, a recording), every framework under the same one; CPU, GPU power, memory and WindowServer CPU come from trials with nothing attached ([why](https://github.com/zeronsh/zgx/blob/main/docs/benchmarking.md#frame-pacing-a-capture-changes-it)).
- Compare within this run only: the same binaries measured hours apart read differently, so a cell is not comparable across runs, while the frameworks in one run share its session.
- Idle memory is two-level: an idle window settles at one of two levels about 25 MB apart, launch to launch, as the Metal driver returns its startup memory. Read idle memory with its range.
- MyGo is immediate mode: each frame it draws builds and draws its whole window, which is how MyGo apps work.
- Binary size is not compared.
- One machine, one session; a personal Mac in use, other applications kept running (the run waited until the machine was quiet). Windows and Linux are not compared here.

The full protocol, its noise and every other series are in the [methodology](/performance/methodology).
